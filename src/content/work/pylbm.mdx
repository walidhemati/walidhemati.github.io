## Problem

Lattice Boltzmann is bandwidth-bound: a D2Q9 update moves at least 72 bytes. The question is whether Python code can sit on that limit. The project started from an existing PyTorch cavity script, which runs at 9 % of the copy bandwidth and turned out to have three boundary-condition bugs, documented in the paper.

## Approach

- An eight-rung ladder from NumPy through PyTorch and `torch.compile` to fused stream–collide kernels.
- The Triton, Warp and Numba kernels are printed from one symbolic description, so all toolchains execute identical arithmetic.
- AA-pattern in-place streaming and 16-bit storage of shifted populations halve the memory traffic.
- Validation: Ghia et al. cavity at Re 100/400/1000, shear-wave viscosity, Poiseuille order 2, Schäfer–Turek cylinder (St 0.2996), 3D Taylor–Green.

## Results

<Results metrics={frontmatter.metrics}>
  On one RTX 3070 Laptop GPU every fused kernel reaches the measured copy bandwidth. FluidX3D, the hand-optimised OpenCL code, runs at the same rate on the same GPU; the PyTorch framework Lettuce is 3.7× slower with its native kernels. See the [paper](https://github.com/walidhemati/pylbm/blob/main/paper/paper.pdf).
</Results>
